# UI 系统重构方案

本方案的目标不是推倒重写，而是在保留当前 UI 系统可用成果的前提下，做一轮“低风险、可分阶段交付、能明显提升统一性和可维护性”的结构重构。

## 1. 结论先说

当前 UI 系统有重构价值，而且已经进入“应该规划重构”的阶段。

原因不是它不能用，而是它已经出现了几类典型信号：

- 核心类职责偏重
- 控件和复合组件实现风格不统一
- 主题应用路径不完全一致
- 焦点系统依赖手动注册，扩展成本会逐渐变高
- 多个复合组件采用“整体重建内部子树”的方式，短期方便，长期不利于维护和状态稳定
- 部分代码已经出现“预留能力存在，但实际接入不完整”的迹象

如果后续只是维护少量菜单，这套系统还可以继续用。
如果后续还会持续扩 UI、增加更多设置页、列表页、弹窗和复杂交互，那么现在开始做定向重构是合适的。

## 2. 当前系统为什么值得重构

## 2.1 统一性不强

这是当前最明显的问题之一。

统一性不足主要体现在：

- 有的组件是纯组合式实现，有的组件把绘制、状态、布局、输入全部写在一个类里
- 有的控件完整使用主题角色，有的控件只部分套主题
- 有的复合控件自己实现 `UiFocusable`，有的则依赖内部子控件
- 有的组件修改配置时局部更新，有的直接整棵 rebuild
- 文本控件、容器控件、交互控件在 reset / theme / rebuild 上的风格不一致

这种不统一最直接的后果不是“代码不好看”，而是：

- 新控件难以照着统一模式实现
- 维护者读代码时需要频繁切换心智模型
- 后续修 bug 时容易改一处漏一处
- 主题、焦点、布局等横切能力更难抽象

## 2.2 核心类职责过重

`UiLayout` 当前同时承担：

- 子节点持有
- 布局计算
- 生命周期分发
- auto-size
- scroll offset 生效点
- transform 生效点

它是系统核心，但也因此承担了过多责任。后面只要继续扩布局能力，它就很容易变成一个越来越重的“总控类”。

`UiScreen` 也同时承担：

- 页面容器
- 开关状态
- 过渡动画
- 输入启用
- 焦点注册
- 焦点导航
- 鼠标点选切焦

这说明系统现在已经有多个“超级节点类”。

## 2.3 复合组件重建过于频繁

`UiMenuList`、`UiOptionList`、`UiTabBar` 这类复合控件大量采用：

- 改数据
- 清空子树
- 重新生成内部子控件

这种方式在原型期非常高效，但随着功能增多会带来问题：

- 临时状态容易丢失
- 回调重新绑定较多
- 主题更新和数据更新容易互相耦合
- 后续做动画、局部刷新、保留滚动位置时会变难

## 2.4 主题应用不完全统一

当前主题系统整体设计方向是对的，但执行上不完全统一。

典型问题：

- 某些控件完整通过 `UiStyle` 应用样式
- 某些控件只部分取主题字段
- 某些复合控件在 `apply_theme()` 中直接重建内部结构
- 某些对象通过 `set_use_theme(false)` 进入半手工风格

这说明“主题是数据层，控件只负责消费主题”的边界还不够稳定。

## 2.5 焦点系统可用，但扩展成本偏高

当前焦点系统能工作，但依赖 `UiScreen` 手动注册 `UiFocusable`。

这意味着：

- 页面稍复杂时，焦点链维护容易漏
- 复合控件内部如果再嵌套复合控件，焦点组织会越来越手工
- 自动可导航树还没有形成

现在这个设计适合小到中型 UI，继续扩展时会逐渐变成维护负担。

## 2.6 已经有一些“结构债务”的信号

例如：

- `UiDialog` 中 `_action_scroll_bar` 已经存在，但当前并未真正挂入子树使用
- `UiOptionList::handle_row_click()` 这类接口存在，但没有真正接入行为链
- `UiLabel::apply_theme()` 和 `UiStyle::apply_label()` 的语义并不完全对齐

这些都说明系统已开始积累“设计想法先行、接线还没完全统一”的债务。

## 3. 这次重构的目标

本次重构建议聚焦在四个目标：

- 提升代码统一性
- 降低核心类复杂度
- 降低复合控件维护成本
- 为后续扩 UI 留出稳定扩展点

更具体地说，希望最终做到：

- 新控件有清晰模板可照着写
- 主题应用只有一条主路径
- 复合控件尽量从“整树重建”转向“数据同步 + 局部刷新”
- 焦点管理从“完全手动组织”演进为“半自动、可推断”

## 4. 这次重构不建议做什么

为了控制风险，这轮不建议做以下事情：

- 不建议重写全部 UI 为另一套框架
- 不建议直接改成立即模式 UI
- 不建议先做跨渲染后端抽象
- 不建议同时重构 UI 和资源系统/输入系统
- 不建议一口气把所有组件都迁移到新范式

换句话说，这轮应该是“体系整理”，不是“技术路线替换”。

## 5. 重构原则

## 5.1 保持外部行为尽量不变

优先保持以下接口稳定：

- 控件公开 setter/getter
- 页面构建方式
- 主题使用方式
- `GameObject` 生命周期接入方式

## 5.2 先统一模式，再扩新能力

不要一边重构一边发散加大量新特性。
先把现有模式整理清楚，再在新结构上长功能。

## 5.3 先治核心骨架，再治边缘控件

优先级应该是：

1. 基类和布局容器
2. 主题和焦点
3. 复合控件
4. 单体控件细节统一

## 5.4 每一步都要可停

每一阶段结束时，都应该形成一个：

- 可编译
- 可运行
- 外部行为可验证

的中间状态。

## 6. 推荐的重构阶段

## 阶段 0：先补文档和约束

这是最便宜也最必要的一步。

需要先明确三类规范：

- 新控件应继承哪一层
- 主题应用应该怎么写
- 复合控件什么时候允许 rebuild，什么时候必须做局部同步

建议补一份内部约定，至少包含：

- 单体控件模板
- 复合控件模板
- `reset()` 规范
- `apply_theme()` 规范
- `on_input()` / `handle_focused_input_event()` 的职责边界

这一步做完，后续改动才不会越改越散。

## 阶段 1：统一基类职责边界

### 目标

减轻 `UiLayout` 和 `UiScreen` 的“超级类”倾向，但不要大面积破坏现有使用方式。

### 建议动作

- 明确 `UiElement` 只负责主题挂接
- 明确 `UiControl` 只负责 enabled/focused 的交互基础
- 给 `UiLayout` 补一个更明确的定位：
  - 它是“线性布局容器”
  - 它不是所有 UI 容器的万能基类
- 评估是否引入更轻量的 `UiContainer` 概念
  - 只负责 child 持有和生命周期分发
  - `UiLayout` 在此基础上额外负责排版

### 为什么值得做

这样可以把“有子节点”和“会布局”拆成两个概念。
以后像 `UiGridLayout`、未来可能的绝对布局容器、Overlay 容器，就不必都绕着 `UiLayout` 的逻辑转。

### 风险

- 会触碰较多容器类
- 如果一次拆太大，容易牵动大量调用点

### 建议策略

先引入新抽象，不急着把所有类都迁过去。
允许一段时间内旧结构和新结构并存。

## 阶段 2：统一主题应用路径

### 目标

让“主题如何进入控件”这件事变得完全一致。

### 建议动作

- 规定所有可主题化控件都优先通过 `UiStyle` 应用样式
- 让 `apply_theme()` 尽量只做“选择主题槽位 + 调用 UiStyle”
- 避免在 `apply_theme()` 里写过多结构重建逻辑
- 修正 `UiLabel` 这类只部分应用 style 的情况，使它完整遵循 `LabelStyle`
- 为复合控件定义“主题作用于结构”还是“主题作用于子控件状态”的统一规则

### 为什么值得做

统一后你会得到：

- 更容易换主题
- 更容易加新主题角色
- 更容易发现某个控件是否偏离主题系统

### 风险

- 个别控件外观可能发生轻微变化
- 需要重新验证已有页面显示是否符合预期

## 阶段 3：统一复合控件的数据驱动方式

### 目标

把复合控件从“改一点就整树重建”逐步改成“数据层驱动 + 局部同步”。

### 优先对象

- `UiMenuList`
- `UiTabBar`
- `UiOptionList`
- `UiDialog`

### 建议动作

- 把数据模型和视图对象生命周期拆开
- 初次构建时创建子控件
- 数据变化时优先：
  - 更新文本
  - 更新 enabled
  - 更新 selected/focused
  - 必要时只增删差异项
- 主题变化时尽量只刷新样式，不重建结构

### 为什么值得做

这一步收益很大，因为它会直接提升：

- 运行期稳定性
- 可维护性
- 后续做动画和局部刷新能力
- 滚动位置和焦点状态保留能力

### 风险

- 会让复合控件内部代码从“短而直白”变成“稍长但结构化”
- 需要更清楚地维护子控件和数据索引关系

## 阶段 4：整理焦点系统

### 目标

把当前“能用但偏手工”的焦点系统，整理成更清晰的规则。

### 建议动作

- 明确页面级焦点与组件级焦点的边界
- 规定复合控件是否作为一个 `UiFocusable` 暴露给 `UiScreen`
- 在复合控件内部统一处理子项焦点，而不是让 `UiScreen` 直接理解内部细节
- 逐步引入“从容器树收集 focusable”的机制
  - 可以先是显式 opt-in
  - 不必一步做到全自动

### 推荐方向

页面只关心一级 focusable：

- `UiMenuList`
- `UiOptionList`
- `UiTabBar`
- `UiTextInput`

而这些组件内部再管理自己的子级焦点。

### 为什么值得做

这会明显降低页面级焦点编排复杂度，也更适合复杂 UI。

## 阶段 5：统一控件实现模板

### 目标

建立“新控件应该长什么样”的统一模板。

### 建议约定

对于单体控件：

- 构造函数只做最少初始化
- `reset()` 负责完整恢复默认状态
- `apply_theme()` 只负责主题应用
- `on_input()` 负责鼠标轮询逻辑
- `handle_focused_input_event()` 负责键盘/手柄逻辑
- 渲染代码尽量不混进状态同步

对于复合控件：

- `reset()` 负责恢复默认配置
- `rebuild_*()` 只用于首次构建或结构变化
- `sync_*()` 负责局部状态刷新
- 主题应用尽量走子控件 style 更新，不直接重建整棵树

### 这一步的价值

以后只要看类名，就大致能猜到：

- 状态在哪
- 样式在哪
- 输入在哪
- 重建和同步分别在哪

这会大幅提升代码统一性。

## 7. 建议新增的规范文档

为了让重构真正稳下来，建议在 `docs` 或开发文档中再加一份“开发规范”。

建议包含这些内容：

- UI 类分层规则
- 样式与主题规则
- 焦点处理规则
- 复合控件构建规则
- 命名规范
- rebuild / sync 的使用边界
- 什么时候允许 `set_use_theme(false)`

## 8. 代码统一性方面建议明确的规则

这是这次重构最应该落地的部分。

## 8.1 命名统一

- 状态字段统一用 `_is_*` / `_has_*` / `_use_*`
- 回调统一命名为 `_on_*`
- 同步方法统一使用 `sync_*`
- 重建方法统一使用 `rebuild_*`
- 主题角色 setter/getter 统一命名为 `set_*_theme_role` / `*_theme_role`

## 8.2 `reset()` 统一

- 所有类都在 `reset()` 中恢复默认状态
- `reset()` 中如需恢复主题角色，必须显式设置
- `reset()` 中如依赖主题，结尾统一 `mark_theme_dirty()`

## 8.3 `apply_theme()` 统一

- 不直接塞业务逻辑
- 不做复杂输入或状态行为
- 优先调用 `UiStyle`
- 只处理主题槽位选择和样式应用

## 8.4 输入职责统一

- `on_input()` 只处理鼠标实时轮询和拖拽
- `on_input_event()` 只处理事件分发层逻辑
- `handle_focused_input_event()` 只处理焦点语义输入

## 8.5 复合控件统一

- 数据模型单独保存
- 子控件集合单独保存
- rebuild 只处理结构变化
- 普通值变化尽量局部同步

## 9. 推荐的实际落地顺序

如果要真的开始改，我建议按下面顺序推进：

1. 先补“重构约束和统一规范”
2. 统一主题应用路径
3. 整理 `UiMenuList`
4. 整理 `UiTabBar`
5. 整理 `UiOptionList`
6. 补齐 `UiDialog` 的结构接线问题
7. 评估是否引入 `UiContainer`
8. 最后再动 `UiScreen` 的焦点组织方式

这个顺序的好处是：

- 前几步收益高
- 风险相对可控
- 不会一开始就碰最危险的核心骨架

## 10. 每阶段的验收标准

建议每阶段都明确验收点。

### 阶段 1 验收

- 容器和布局职责边界更清晰
- 没有行为回归

### 阶段 2 验收

- 主题应用路径统一
- 各控件 `apply_theme()` 风格基本一致

### 阶段 3 验收

- `UiMenuList` / `UiTabBar` / `UiOptionList` 不再频繁整树重建
- 焦点、滚动位置、值状态更稳定

### 阶段 4 验收

- 页面级焦点注册代码更少
- 复合控件内部焦点边界更清楚

### 阶段 5 验收

- 新增一个控件时，能明显按统一模板实现
- 看类结构时能快速定位状态、渲染、输入、主题和同步逻辑

## 11. 预期收益

如果按这个方案完成，最终会获得：

- 更强的代码统一性
- 更低的维护成本
- 更稳定的复合控件行为
- 更容易扩新页面和新控件
- 更清晰的主题系统
- 更容易测试和排查问题的 UI 结构

## 12. 最终建议

我的建议是：

- 有必要重构
- 但应做“结构整理型重构”，不做“推倒重写型重构”
- 最值得优先投入的是统一性，而不是花哨新特性

一句话总结：

这套 UI 系统的方向是对的，但现在已经需要从“能工作”升级到“能稳定扩展”。这次重构最核心的任务，不是换框架，而是把基类、主题、焦点、复合控件这几条主线统一起来。

## 13. 后续可直接展开的实施项

如果下一步要正式开工，我建议先从这三个最划算的点开始：

- 先统一 `apply_theme()` 规则，并修正 `UiLabel` 等不完全一致的控件
- 再把 `UiMenuList` 和 `UiTabBar` 从 rebuild-heavy 改成局部同步
- 最后再处理 `UiOptionList`，因为它最复杂，也最能体现收益
